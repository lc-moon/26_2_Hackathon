# 발표

> 발표 구성, 질의응답 대비, UI 구성 근거. 발표 대본 전문과 슬라이드 제작 프롬프트는 로컬 `발표자료/`에만 있고 저장소에는 올리지 않았다.
> 결과: **대상(1등)**. 발표는 2026-11-06(금), 5분 + 질의 5분.

## 1. 발표 구성 (11장)

디자인씽킹 흐름(공감 → 페르소나 → 문제 정의 → 아이디어 → 구현 → 테스트)을 심사 기준(문제 공감·해결 완성도·AI 활용·발표력)에 맞춰 11장으로 줄였다. 슬라이드는 Claude Design으로 만들고 화면 이미지 형태로 내려받았다.

| 장 | 내용 | 말하는 시간(추정) |
|---|---|---|
| 1 | 표지 + 팀 (팀 전공 세 가지) | 20초 |
| 2 | 오프닝 영상 (슬라이드 전체) | 영상 + 11초 |
| 3 | 공감 + 페르소나: "몇 층 높이에 있느냐?" | 17초 |
| 4 | 문제 정의(POV·HMW) + 아이디어 4개 → "자동 감지 + 3D 위치" | 18초 |
| 5 | 핵심 기능 3가지: ALERT → LOCATE → RESPOND, "센서는 미래 가정" | 15초 |
| 6 | 데모 ① 평시 (영상) | 9초 + 영상 |
| 7 | 데모 ② 높이 정보·자동 신고 없음 (영상) | 19초 + 영상 |
| 8 | 데모 ③ 공중 추돌, 3D 좌표 자동 전송 (영상) | 22초 + 영상 |
| 9 | AI를 믿지 않고 확인했다 | 31초 |
| 10 | 성과·배운 점·향후 | 26초 |
| 11 | 마무리·Q&A, 출처 | 16초 |

합계 약 4분 28초(말 약 3분 24초 + 영상 약 1분 4초). 글자 수로 계산한 추정치다.

**핵심 메시지 세 가지**
1. 사고 위치는 "어디"뿐 아니라 "몇 층 높이"까지 알아야 구조가 빠르다
2. 높이 정보와 자동 신고가 있을 때(③ 약 5분 도달)와 없을 때(② 약 19분 접근, 골든타임 상실)를 시뮬레이션으로 비교했다
3. AI와 함께 만들되 AI의 말을 그대로 믿지 않고 확인해서 고쳤다 (예: AI가 쓴 "GPS는 2차원"을 사실 확인 후 정정)

**데모는 영상으로 넣었다.** 시나리오 ①②③ 순서로 약 10초 / 18초 / 18초. 라이브는 지도 로딩과 인터넷 상태 때문에 위험해서 녹화를 주로 쓰고 사이트 주소는 보조로 뒀다.

## 2. UI 구성 근거 (질문: "좌·우·하단 패널 구성은 무엇을 근거로 했나요?")

**전제**: 정식 요구사항 정의서를 먼저 쓰고 만든 것이 아니다. 구조대가 현장에 접근하며 던지는 질문의 순서(무슨 사고 → 어디 → 누가 위험 → 어떻게 가나 → 주변은 안전한가)로 나눴고, **만든 뒤에** 공개 표준·업무 흐름과 대조했다. 레이아웃은 UAM 구조 지원 예시 웹앱을 참고했다. 실제 119 상황실 화면은 공개 자료에서 찾지 못했다.

| 패널 | 구조대의 질문 | 대조한 근거 |
|---|---|---|
| 좌 · 사고 개요 | 무슨 사고인가? | 119 접수 절차 "신고접수 → 기본 정보 표시", 표준 SSF-ST-T-0017 이벤트 모니터링(S-119-R004·R005) |
| 좌 · 3축 좌표 | 어디인가, 몇 m 높이인가? | 우리 문제 정의. 표준의 WGS84 좌표계에 고도(Z)를 더함 |
| 좌 · 타임라인 | 언제 무슨 일이 있었나? | 표준의 이벤트 진행상황·상황이력(R007·R008), "사건 진행 상황관리" |
| 우 · 탑승자 | 누가 위험한가? | **기존 119 근거 없음.** 예시 웹앱과 우리 가정(웨어러블·좌석 센서). 모든 값은 가상 |
| 하 · 3D 측위 | 위치를 믿어도 되나? | 신고 위치정보가 부정확하다는 문제, 2026.6 정부 정밀측위 시범 보도 |
| 하 · 출동·접근 | 구조차는 어디쯤인가? | 표준의 소방차량 이동위치 목록(R006), "출동대 편성 → 출동지령" |
| 하 · 현장 2차 위험 | 접근해도 안전한가? | 서울시 U-City 센터가 119 상황실 요청 시 도로·위험시설 정보를 준 연계 사례(2015 기사, 검색 요약만 확인). 2차 충돌 회피는 우리 시나리오의 핵심 |

**답변 (20초)**
> "실제 119 상황관제 화면은 공개된 것을 찾지 못했습니다. 그래서 구조대가 현장에 접근하며 던지는 질문, 즉 무슨 사고인지, 어디인지, 누가 위험한지, 어떻게 가는지, 주변은 안전한지의 순서로 패널을 나눴습니다. 만든 뒤에는 공개된 119 접수·관제 업무 흐름과 스마트도시 119 긴급출동 지원서비스 표준의 상황관제 항목과 대조해서, 사고 개요, 이력, 소방차량 위치 같은 핵심이 대응되는 것을 확인했습니다. 화면 배치는 UAM 구조 지원 예시 웹앱을 참고했습니다."

하면 안 되는 말: "119 시스템을 분석해서 만들었다", "실제 119 화면과 같다", "내부 시스템이라 절대 볼 수 없다".

## 3. 예상 질문과 답변

- **GPS에 고도가 있다면 뭐가 새로워요?** GPS 신호에는 고도 값이 있지만 기존 신고·관제·지도는 수평 위치 중심이라 높이를 자동으로 전달하고 입체로 보여 주는 데 한계가 있다. 정부도 층 정보를 주는 정밀측위를 시범 중이다(2026.6 보도). 우리는 그 문제를 공중 사고에 적용해 3D 좌표 자동 전송, 3D 지도 표시, 위에서 접근하는 구조까지 이었다. 수치는 모두 가정
- **센서는 정말 가능한가요?** 미래 가정이다. 우리가 만든 것은 센서 신호가 오면 그 위에서 3D 위치를 전달·표시하고 구조 접근을 안내하는 시스템 시뮬레이션
- **5분, 19분, ±3m 같은 숫자의 근거는?** 모두 가정값. 높이 정보가 있을 때와 없을 때 구조 흐름이 어떻게 달라지는지 보여 주는 것이 목적
- **실제 119와 연계할 수 있나요?** 향후 과제. 실제 3D 지도·센서 연동, 위치 정확도 검증, 긴급기관 연계 검토가 필요
- **AI는 어디까지 썼나요?** 구현 전반에 Claude Code. 다만 결과를 그대로 쓰지 않고 "GPS는 2차원" 표현을 정정했고, 수치를 가정값으로 표기했고, 차량 겹침·렉·가독성을 직접 확인해 고쳤다
- **사용자 테스트는 했나요?** 아직 못 했다. 화면 크기별 확인, 차량 겹침 검사, 배포 주소에서 지도 동작을 확인했고 사용자 반응은 향후 과제
- **지도·3D 모델 출처는?** 지도 브이월드(국토교통부), 차량 NEW TESLA ROADSTER 2027(yarifmx), 목격자 Low Poly Man Taking Phone While Walking(ROH3D). Sketchfab CC BY 4.0, 마지막 장에 표기
- **2D 지도로는 왜 안 되나요?** 같은 위도·경도라도 건물 사이에서 높이가 다르면 접근 경로가 달라지고, 높이를 모르고 접근하면 2차 충돌 위험이 있다
- **애니메이션은 어떻게 만들었나요?** 물리 엔진이 아니라 시간 함수로 연출한 시각화. 3D는 브이월드 안의 Cesium. `구현_이해하기.md` 참고
- **시스템이 어떤 기존 시스템을 참고했나요?** 위 §2 참고. 레이아웃은 예시 웹앱, 업무 흐름은 공개 자료와 표준을 사후 대조

- "119 시스템 화면을 찾지 못했다"와 "비공개다"는 다르다
